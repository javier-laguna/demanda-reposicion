# E0 · Base del repo y gobierno

## Objetivo

Dejar un repo reproducible y seguro antes de escribir lógica: ambiente fijado, validación automática, datos y
secretos fuera de git, y la documentación de proceso lista para llenarse etapa por etapa.

## Entregables

- `pyproject.toml` + `uv.lock` + `.python-version` (3.13). Dependencias de desarrollo: ruff, pyrefly, pytest,
  pre-commit.
- `Makefile` con `setup`, `data`, `lint`, `format`, `types`, `test`, `validate`, `docker-build` y `up`.
- `src/demanda/config.py` (pydantic-settings, `SecretStr`) y `.env.example`.
- `src/demanda/datos/fuente.py` + `demanda data`: copia los CSV desde el zip o una carpeta a `data/raw/` y verifica
  `data/manifest.sha256`.
- `.gitignore` y `.dockerignore` (datos, artefactos, secretos, recibos de archify).
- `.pre-commit-config.yaml`: ruff, pyrefly, gitleaks, archivos grandes y un hook que bloquea `csv`/`parquet`/`zip`.
- Esqueletos de `Dockerfile`, `compose.yaml` y `.github/workflows/ci.yml`.
- `CLAUDE.md`, `PROCESS.md`, `docs/specs/` y `.claude/agents/`.
- Diagrama de arquitectura con el nodo de monitor de drift.

## Criterios de aceptación

- `make setup && make data DATA_SRC=... && make validate` pasa.
- `pre-commit run --all-files` en verde.
- `git status` no muestra datos, zip, `.env` ni artefactos.

## Resultado

- Todo lo anterior queda en verde. `make data` verifica los 3 hashes desde el zip original y `make validate` pasa
  (4 tests de `fuente`).
- Docker: `docker compose build` construye la imagen y `docker compose run --rm demanda` verifica los hashes dentro
  del contenedor, montando `data/` como volumen.
- **Decisiones tomadas en esta etapa:**
  - commits en `main`;
  - los datos nunca se versionan, solo sus hashes;
  - la caché de insights agregados sí se versiona;
  - la GPU disponible queda fuera de la ruta crítica, porque todo debe correr en CPU.
